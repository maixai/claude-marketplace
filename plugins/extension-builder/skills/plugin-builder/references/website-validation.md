# 网站双链验收

plugin-builder 制定验证计划和交付前读取；只在已批准范围执行。先读取目标仓库实际 package scripts、采集器和测试，避免按旧命令猜环境。

## 插件链与网站链

插件链按 [共享验证](../../../references/validation.md) 检查结构、组件集成、受控加载、行为和兼容。网站链独立检查：市场登记 → manifest/组件/README → catalog → 页面。任一链缺证据都单列，不互相抵消。

当前市场已有入口（在目标仓库根运行；执行前核对仍存在且依赖已就绪，不自动安装）：

```bash
node --test site/scripts/collect-plugins.test.mjs
node --test scripts/plugin-update-times.test.mjs
npm run catalog
npm run build
```

类型检查使用当前 package scripts 已定义的入口，不发明新包装脚本。记录每项原始命令、结果和对应产物。采集 fixture 用于离线错误分支；网站端到端使用真实插件条目，不能用临时 mock catalog 代替。

## 页面验证清单

按项目 Chrome DevTools 规则，由实际具备工具与授权的 Main 执行；developer 的固定白名单没有浏览器能力。

1. `list_pages` 复用已有页面；必要时打开获准站点。等待目标内容出现再截图，避免截到加载状态。
2. 检查目标卡片的标题、简介、关键词、版本和更新时间语义，进入详情核对目标 name。
3. 核对安装步骤和复制操作；与真实市场名、插件名一致，不只看按钮存在。
4. 核对组件数量、名称、描述与模型，识别漏项/重复；README 实际用法可读，链接、图片、锚点按实际目标验证。
5. 查看控制台，检查相关网络请求及完整请求/响应；有新错误就定位，不把构建通过当运行无错。
6. 受影响布局覆盖必要断点，先等待再截图。维护仅回归受影响页面/交互，新增插件检查目标完整展示；无关全站问题只报告。
7. 记录页面/截图/检查结果与对应代码状态，关闭非必要测试页，清理获准测试进程。

工具不可用、连接被拒或页面环境缺失时明确 `未验证/阻塞`；不改 MCP 设置，不用替代 CLI/SDK 绕过连接。是否允许修复环境由用户另行决定。用户说已恢复但会话仍无工具时，以可观察能力报告，不沿用历史故障结论当现状。

## 完成判据

静态、采集、类型和构建成功不证明浏览器交互通过。浏览器通过也不证明插件真实加载或模型路由。独立 reviewer 输入包含两条链的原始证据及所有未验证项，只有批准成功标准的必要证据齐备才整体通过。

若新组件类型超出现有采集覆盖，先回设计与批准，不静默改全站或漏展示。证据与产物变化的处理沿用共享验证协议。
